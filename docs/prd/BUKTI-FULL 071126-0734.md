# Full Chromium capability evidence

This file records what full Chromium **actually did** when the `chrome-full`
adapter drove it inside Xvfb, and what it did not do. It is the only source for
`TERUKUR_FULL` in `crates/policy/src/select.rs`. Nothing here comes from
Chromium's documentation or from an assumption about what a "real browser"
should be able to do.

## Why this is measured on the laptop and not in CI

The adapter needs two things a stock runner does not have ready: a full
Chromium (not `chrome-headless-shell`, which is what Playwright ships) and an X
server. Both exist on the development host at `/usr/bin/google-chrome` and
`/usr/bin/Xvfb`, so the probe runs where the adapter is supposed to run. The
probe skips itself with an explicit message when either binary is missing, so
`cargo test` stays green on a host that has neither.

## Probe results

Run `cargo test -p browserd --test penuh_probe -- --nocapture`, 1 passed, 0
failed.

| Probe | Result | Observed |
|---|---|---|
| `display` | ok | `:102`, a display that did not exist before the boot |
| `boot` | ok | 3217 ms, parent pid alive, `Chrome/156.0.8078.79` |
| `webdriver` | ok | `false` (the boolean, evaluated in the page) |
| `user_agent` | ok | `Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/156.0.0.0 Safari/537.36` |
| `layout` | ok | title `probe-full` read from the fixture served over HTTP, element box `{"x":0,"y":21.4375,"width":1200,"height":600,...}`, screenshot 12820 base64 characters |
| `script` | ok | `document.body.dataset.skrip` = `ya`: the page's own inline script ran |
| `cookies` | ok | cookie `probe=ya` written through `Network.setCookie` came back through `Network.getCookies` with the same value |
| `input` | ok | `Input.dispatchMouseEvent` at the element's centre changed the DOM: `dataset.klik` = `ya` |
| `rss_mb` | ok | 1490 MB across 15 processes (1660 MB / 17 processes on a colder run) |
| teardown | ok | after `stop()` the engine is not running and the Xvfb display is gone |

The one fact this milestone exists for is `webdriver: false`. A
`chrome-headless-shell` born with `--headless` reports `true`; the same Chromium
running headed on a virtual display reports `false`, and that is the whole
difference the adapter buys.

## Boot time varies with host load, and that was measured too

Six runs, same binary, same fixture:

| Run | Host state | Boot | RSS |
|---|---|---|---|
| 1 | 36 orphaned `chrome-headless-shell` processes from earlier test suites still alive, 4.9 GB RSS between them | 9741 ms | 1634 MB / 18 |
| 2 | same load, ready timeout at 30 s | timed out at 30 s | not reached |
| 3 | same load, ready timeout still 30 s | 11812 ms | 1496 MB / 15 |
| 4 | orphans killed, host quiet | 3329 ms | 1660 MB / 17 |
| 5 | quiet | 7329 ms | 1642 MB / 17 |
| 6 | quiet, ready timeout raised to 60 s | 3217 ms | 1490 MB / 15 |

Two consequences, both written into the code rather than into a hope:

1. The probe's ready timeout is 60 seconds, not the adapter default of 30. Boot
   measured 3.2 to 11.8 seconds on this host, and one run crossed 30 seconds
   purely because other tests had left their browsers behind. The timeout is a
   ceiling on patience; the reported number is still the real boot time.
2. The load was not a mystery, it was a leak: 36 leaked browser instances from
   `sesi_live`, `m4_proof`, `diagnostik`, and `idle_proof` were still running,
   reparented to `systemd --user`, still listening on their own debugging ports.
   They were killed before runs 4 to 6. That leak is a real defect in the other
   test suites' teardown and is recorded as a backlog item; it is not caused by
   this adapter, whose stop path does remove its display.

## What the capability table now says

| Capability | Value | Basis |
|---|---|---|
| `layout` | `true` | the fixture was fetched over HTTP, the DOM was built, the title and an element box were read, and a screenshot came out as a real PNG |
| `script` | `true` | the page's own inline script ran |
| `cookies` | `true` | written then read back, same value |
| `input` | `true` | a dispatched mouse event reached the page and changed the DOM |

`layout: true` means "loads a page and renders it to PNG". It does not mean the
pixels were compared against a reference rendering, because they were not.

## What is deliberately not claimed

- The anti-bot detection rate on any real host. `navigator.webdriver == false`
  is one signal out of many; whether it is enough to pass a single challenge was
  not measured, and no document in this repo should imply it was.
- Memory at scale. The numbers above are one engine with one tab. Six tabs on
  full Chromium were not measured, so no per-tab figure is claimed.
- Stability over hours. Every run here lasted seconds.

## Reproducing

```bash
cd ~/src/opencrabs-browser
cargo test -p browserd --test penuh_probe -- --nocapture
```

The probe prints `PROBE <name>: ok|GAGAL <detail>` for every check and a
markdown table at the end. It needs `/usr/bin/google-chrome` (or
`CHROME_FULL_BIN`) and `/usr/bin/Xvfb` (or `XVFB_BIN`); without them it prints a
skip message and returns.
