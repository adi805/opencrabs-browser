## Findings

### 1. The `--port` default pointed at the production port (already fixed)

`crates/browserd/src/cli.rs:162-164` gave `--port` a default of `9222`, which is the
production browser port, while the comment on the line above claimed, in Indonesian,
that the port is deliberately 9224 during development so the production browser on
9222 is left untouched. The comment and the code contradicted each other.

Precedence inside `Resolved::resolve` (`crates/browserd/src/daemon.rs:938-941`):
`args.bind` wins, then `file.daemon.bind`, then `127.0.0.1:{args.port}`. So a plain
`browserd serve` with no flag and no config file would try to bind
**127.0.0.1:9222**.

On this host that was masked because the systemd unit sends
`--bind 127.0.0.1:9224`, but the default was still a trap, and this is exactly what
AC-019 is about. Already fixed: `crates/browserd/src/cli.rs:165` now defaults to
9224, and the `Resolved::resolve` chain is locked by four tests in
`crates/browserd/src/daemon.rs` plus the live check in
`crates/browserd/tests/isolasi_port.rs`.

### 2. Per-host routing (now wired, AC-007)

The host-rule engine selection logic existed and was unit tested in
`crates/policy/src/select.rs`, but it had no caller outside that file. Target
creation always used the default engine (`crates/cdp/src/targets.rs:270`). The
consequence: the host rules had never influenced a real path, so AC-007 could not
be called Verified.

Fixed in this round. `crates/browserd/src/routing.rs` provides `PemilihPolicy`,
which wraps `policy::PolicySection` plus the engine catalog and implements
`cdp::PemilihMesin`; the daemon wires it through
`ProxyState::pool(..).with_observer(..).with_pemilih(..)`
(`crates/browserd/src/daemon.rs`), and `crates/cdp/src/mux/peta.rs` calls it in the
`Target.createTarget` branch when the client names no explicit engine. The evidence:
`cargo test -p browserd --test routing_host` (4 tests, a real proxy plus two fake
engines of different kinds; the rule `toko.test` -> `chrome-full` lands on the
`full` instance, an explicit client choice still wins, an uninstalled kind answers
`-32000`), plus 5 unit tests in `crates/cdp/src/mux/peta/uji.rs` that check the
rejection path and the assignment path. The `/json/new` path deliberately keeps
using the default engine because it carries no URL that could be mapped to a host.

## Production port isolation (AC-019)

It is now an automatic test, no longer a manual procedure.

`cargo test -p browserd --test isolasi_port` runs the chain that used to be done by
hand, under one hard rule: port 9222 is only ever read, never written.

| Step | Result that must be visible |
|---|---|
| Read the target count on 9222 before (GET only) | `None` if nothing is listening, a number if something is |
| Start `browserd serve` on a random port with a temporary profile, open one tab (`/json/new`) | a real Chromium engine is born |
| Read `DevToolsActivePort` in the engine profile | the engine debug port, 37107 on this run, not 9222 |
| Re-read the target count on 9222 | must be identical to the state before |

A change from `None` to `Some` is caught too: a development daemon that grabbed 9222
would raise a listener there. The check is skipped with a clear message when
`chrome-headless-shell` is missing, so `cargo test` stays green on a machine without
a browser. The live checks are serialized through a host-wide lock
(`crates/browserd/tests/common/mod.rs`) so two Chromiums are never born at once.

Four unit tests in `crates/browserd/src/daemon.rs` lock the `Resolved::resolve`
chain ahead of the live check: the default bind can never end up on `:9222`,
`[daemon]` without `bind` still means 9224, 9222 is only reachable through a `bind`
the operator wrote themselves, and the engine default profile lives in
`.cache/opencrabs-browser`, separate from the 9222 profile.
