## Temuan

### 1. Default `--port` menunjuk port produksi (sudah diperbaiki)

`crates/browserd/src/cli.rs:162-164` memberi `--port` default `9222`, yaitu port browser produksi, sementara komentar di baris di atasnya mengklaim "Sengaja 9224 saat pengembangan supaya browser produksi di 9222 tidak tersentuh". Komentar dan kode saling bertentangan.

Presedensi di `Resolved::resolve` (`crates/browserd/src/daemon.rs:938-941`): `args.bind` menang, lalu `file.daemon.bind`, lalu `127.0.0.1:{args.port}`. Jadi `browserd serve` polos tanpa flag dan tanpa berkas config akan mencoba bind **127.0.0.1:9222**.

Di host ini tertutupi karena unit systemd mengirim `--bind 127.0.0.1:9224`, tapi default-nya tetap jebakan, dan ini persis yang dimaksud AC-019. Sudah diperbaiki: `crates/browserd/src/cli.rs:165` memakai default 9224, dan rantai `Resolved::resolve` dikunci empat test di `crates/browserd/src/daemon.rs` plus uji live `crates/browserd/tests/isolasi_port.rs`.

### 2. Routing per host (sudah tersambung, AC-007)

Logika pemilihan mesin berbasis aturan host ada dan teruji unit di `crates/policy/src/select.rs`, tetapi tidak ada satu pun pemanggil di luar berkas itu. Pembuatan target selalu memakai mesin bawaan (`crates/cdp/src/targets.rs:270`). Konsekuensinya: aturan host belum pernah berpengaruh di jalur nyata, jadi AC-007 belum boleh disebut Verified.

Sudah diperbaiki di putaran ini. `crates/browserd/src/routing.rs` menyediakan `PemilihPolicy` yang membungkus `policy::PolicySection` + katalog mesin dan mengimplementasikan `cdp::PemilihMesin`; daemon menyambungkannya lewat `ProxyState::pool(..).with_observer(..).with_pemilih(..)` (`crates/browserd/src/daemon.rs`), dan `crates/cdp/src/mux/peta.rs` memanggilnya di cabang `Target.createTarget` saat klien tidak menyebut mesin eksplisit. Buktinya: `cargo test -p browserd --test routing_host` (4 test, proxy nyata + dua mesin palsu beda jenis; aturan `toko.test` -> `chrome-full` mendarat di instance `full`, eksplisit klien tetap menang, jenis tak terpasang dijawab `-32000`), plus 5 test unit di `crates/cdp/src/mux/peta/uji.rs` yang memeriksa jalur penolakan dan jalur penugasan. Jalur `/json/new` sengaja tetap memakai mesin bawaan karena tidak membawa URL yang bisa dipetakan ke host.

## Yang belum terukur

Tiga hal ini sengaja tidak diklaim, karena buktinya belum ada:

1. `Gudang::pegang` (lease) belum dipanggil dari jalur produksi mana pun; perilaku lease versus reap baru terbukti di test `idle_reap.rs`.
2. TTL handoff 900 detik masih diuji dengan jam semu, belum live.
3. `loop_anggaran` belum diuji end-to-end dengan mesin nyata; yang teruji adalah keputusan per-mesin dan pencatatannya.

## Isolasi port produksi (AC-019)

Sudah jadi test otomatis, bukan lagi prosedur manual.

`cargo test -p browserd --test isolasi_port` menjalankan rantai yang dulu dikerjakan tangan, dengan satu aturan keras: port 9222 hanya dibaca, tidak pernah ditulis.

| Langkah | Hasil yang harus terlihat |
|---|---|
| Baca jumlah target di 9222 sebelum (GET saja) | `None` kalau tidak ada yang mendengarkan, angka kalau ada |
| Nyalakan `browserd serve` di port acak dengan profil sementara, buat satu tab (`/json/new`) | mesin Chromium nyata lahir |
| Baca `DevToolsActivePort` di profil mesin | port debug mesin, pada run ini 37107, bukan 9222 |
| Baca ulang jumlah target di 9222 | harus identik dengan keadaan sebelum |

Perubahan `None` menjadi `Some` ikut tertangkap: daemon pengembangan yang menyerobot 9222 akan menyalakan listener di sana. Uji dilewati dengan pesan jelas kalau `chrome-headless-shell` tidak ada, supaya `cargo test` tetap hijau di mesin tanpa browser. Uji live diserialkan lewat kunci host-wide (`crates/browserd/tests/common/mod.rs`) supaya dua Chromium tidak lahir bersamaan.

Empat test unit di `crates/browserd/src/daemon.rs` mengunci rantai `Resolved::resolve` di depan uji live: bind bawaan mustahil berakhir `:9222`, `[daemon]` tanpa `bind` tetap 9224, 9222 hanya tercapai lewat `bind` yang ditulis operator sendiri, dan profil bawaan mesin ada di `.cache/opencrabs-browser`, terpisah dari profil 9222.
