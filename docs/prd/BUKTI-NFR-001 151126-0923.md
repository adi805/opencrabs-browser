# Bukti NFR-001 / AC-014: cache layout pada tangkapan layar

Catatan kerja 15 November 2026. Semua angka di bawah keluar dari perintah yang
tertulis di berkas ini, bukan dari ingatan.

## 1. Temuan yang mengubah cara mengukur

Angka "25,9 detik" yang beredar untuk halaman 1.206 elemen berasal dari binary
**debug** (`/mnt/hdd/OpenCrabs/build/cargo/debug/browserd`). Itu bukan
pengukuran yang sah untuk requirement performa: profil `dev` tanpa optimasi
tidak mewakili apa pun yang dikirim ke pemakai. Diukur ulang dengan binary
**release** pada pohon yang sama, halaman itu sudah jauh di bawah ambang:

| Binary | p50 | p95 | ms/simpul p50 | AC-014 (p95 < 4.000 ms) |
|---|---|---|---|---|
| debug, tanpa cache | 20.025,9 ms | 23.684,8 ms | 16,61 | GAGAL |
| release, tanpa cache | 578,2 ms | 740,4 ms | 0,48 | **LULUS** |

Perintah (release): `OC_BROWSERD=/tmp/ocb-tuntas/browserd-sebelum-release python3
/tmp/ocb-tuntas/p95.py "release-SEBELUM" 9270 http://127.0.0.1:8099/b600.html 10`.

Jadi AC-014 **sudah lulus sebelum perubahan apa pun**, dan yang salah bukan
mesinnya melainkan binary yang dipakai mengukur. Ini dicatat di depan supaya
angka sesudah tidak dibaca sebagai "cache menyelamatkan requirement".

## 2. Kenapa cache tetap dikerjakan

Layout dihitung **di dalam** pelukis: `paint::lukis_penuh` memanggil
`layout::hitung_dengan_font` setiap kali melukis. Akibatnya setiap tangkapan
layar menata ulang seluruh dokumen, walau pohonnya tidak berubah sejak
tangkapan sebelumnya. Biaya itu terukur di binary debug:

```
$ /mnt/hdd/OpenCrabs/build/cargo/debug/examples/ukur_layout /tmp/ocb-audit/www/b600.html
simpul      : 2408
parse       :     95.8 ms
layout #1   :  14479.8 ms  (1807 kotak)
layout #2   :  13162.5 ms  (1807 kotak)
layout #3   :  14822.5 ms  (1807 kotak)
lukis #1    :  19861.7 ms  (93970 byte, 0 kotak)
lukis #2    :  19098.7 ms  (93970 byte, 0 kotak)
lukis #3    :  20910.9 ms  (93970 byte, 0 kotak)
```

Selisih `lukis` dan `layout` (±5 detik di debug) adalah biaya melukis murni;
sisanya layout yang diulang. Pada release proporsinya lebih kecil, tapi
bentuknya sama: pekerjaan yang sama dibayar berkali-kali untuk pohon yang
tidak berubah.

## 3. Yang diubah

| Berkas | Perubahan |
|---|---|
| `crates/engine/src/native/js.rs` | Cache layout `Halaman` dikunci `(versi pohon, lebar, tinggi)`, bukan versi saja. Pintu `layout_untuk(dok, viewport)` dipublikasikan. |
| `crates/engine/src/native/paint.rs` | `lukis_dari_laporan(...)`: melukis dari laporan layout yang sudah dihitung; `lukis_penuh` menata lalu memanggilnya, jadi tidak ada jalur kedua yang dirawat terpisah. |
| `crates/cdp/src/native_wire/state.rs` | `Page.captureScreenshot` memakai `halaman.layout_untuk(&dok, viewport)`; kalau tidak ada konteks halaman, jatuh ke jalur lama yang menata ulang. |

Viewport masuk kunci karena laporan yang sama tidak sah untuk ukuran jendela
lain (`width: 100%`, `@media`), dan memakai ulang laporan lebar lama adalah
cara paling halus membuat tangkapan salah tanpa galat.

## 4. Bukti cache tidak menyajikan layout basi

Kesegaran dijamin `Halaman::versi`, yang dinaikkan jembatan DOM untuk setiap
operasi yang mengubah pohon (`setText`, `setAttr`, `delAttr`, `create`,
`createText`, `append`, `insertBefore`, `remove`, `setTitle`, `attachShadow`,
`setHtml`, `insertHtml`, `clone`). Dua tes menjaga tepat di situ, dan
keduanya dibuktikan **merah** lebih dulu:

1. `crates/engine/src/native/js.rs` → `cache_layout_dibuang_saat_pohon_berubah`
   - rusak dengan sengaja (kunci versi dipatok `0`):
     `left: "50"  right: "120"` → FAILED, 0 passed / 1 failed.
   - dipulihkan: `test result: ok. 1 passed; 0 failed`.
2. `crates/cdp/tests/native_state.rs` → `capture_screenshot_memakai_ulang_layout_dan_tetap_segar`
   - dua tangkapan berturut-turut tanpa mutasi harus **identik byte**;
   - sesudah `setAttribute` mengubah lebar dan warna, tangkapan harus berbeda.
   Hasil: `test result: ok. 7 passed; 0 failed` (seluruh tes `capture_screenshot*`).

Satu arah saja tidak membedakan apa pun: pelukis yang selalu menata ulang juga
lolos "berubah jadi segar", dan pelukis yang selalu memakai cache juga lolos
"dua kali sama".

## 5. Angka sesudah

Perintah: `OC_BROWSERD=/tmp/ocb-tuntas/browserd-sesudah-release python3
/tmp/ocb-tuntas/p95.py "release-SESUDAH" 9300 http://127.0.0.1:8099/b600.html 10`.
Halaman yang sama (`b600.html`, 1.206 elemen), binary release pada pohon yang
sama, sepuluh tangkapan berturut-turut tanpa navigasi ulang.

| Ukuran | Tanpa cache | Dengan cache | Perubahan |
|---|---|---|---|
| p50 | 578,2 ms | **113,4 ms** | 5,10x lebih cepat |
| p95 | 740,4 ms | **251,3 ms** | 2,95x lebih cepat |
| maks | 791,1 ms | 358,6 ms | |
| ms/simpul p50 | 0,48 | **0,09** | |
| ms/simpul p95 | 0,61 | 0,21 | |

Sampel mentah sesudah cache: `358,6 · 113,1 · 112,2 · 111,7 · 120,2 · 113,3 ·
113,4 · 117,5 · 116,5 · 112,5` ms. Tangkapan pertama masih 3x lebih lambat
karena ia yang membayar layout penuh; sisanya hanya melukis. Itu justru bentuk
yang diharapkan dari cache: biaya layout dibayar sekali per versi pohon.

Debug, dengan cache (halaman yang sama): p50 20.025,9 → **6.157,1 ms** (3,25x).
Angka debug dipakai hanya sebagai pembanding internal, bukan bukti AC.

## 6. Kesimpulan

| Butir | Status |
|---|---|
| AC-014 (p95 < 4.000 ms) | **LULUS**: 251,3 ms dengan cache; 740,4 ms bahkan tanpa cache |
| FR-006 / AC-007 (3,0 ms/simpul) | **LULUS**: 0,09 ms/simpul p50, 0,21 ms/simpul p95 |
| Layout tidak basi sesudah mutasi DOM | dijaga dua tes, keduanya dibuktikan merah dulu |
| Cache tidak dipakai untuk viewport lain | kunci `(versi, lebar, tinggi)` |

Catatan jujur: klaim lama "25,9 detik untuk 1.206 simpul" adalah angka binary
debug, dan requirement performa tidak boleh dinilai dari profil `dev`. Angka
release sebelum cache sudah lulus AC-014, jadi nilai perubahan ini bukan
"menyelamatkan requirement" melainkan menghapus pekerjaan berulang: 5,1x pada
p50 dan 465 ms per tangkapan yang tidak perlu dibayar lagi.
